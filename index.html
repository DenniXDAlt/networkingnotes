Phase 1

Source Packaging — Encapsulation Down the OSI Stack

2 min

Core idea

The application data is wrapped layer-by-layer as it moves down the stack. Each layer adds its own header (and Layer 2 adds a trailer). This process is called encapsulation.

Layer-by-layer breakdown

Layer 7 — ApplicationHTTP request generated → PDU called Data / Message
Layer 4 — TransportAdds port numbers header → PDU = Segment. (For this exam: just know it passes PDUs down for encapsulation. No TCP/UDP mechanism detail required.)
Layer 3 — NetworkAdds IPv4 header (Src IP, Dst IP, TTL, Protocol) → PDU = Packet
Layer 2 — Data LinkAdds Ethernet header (Src MAC, Dst MAC, EtherType) + Trailer (FCS/CRC) → PDU = Frame
Layer 1 — PhysicalConverts frame to bits (electrical/light/radio signals) onto the medium

IPv4 Packet Header — key fields

Source IP: 192.168.10.10 ← NEVER changes end-to-end
Destination IP: 172.16.1.99 ← NEVER changes end-to-end
TTL: 128 ← decremented by 1 at each router hop
Protocol: 0x06 (TCP) ← tells Layer 3 what's inside the packet

Ethernet Frame — Layer 2 fields (first hop: PC → R1)

Src MAC: AA-AA (PC NIC)
Dst MAC: BB-BB (R1 G0/0/0 — the default gateway, NOT the web server!)
EtherType: 0x0800 (IPv4)
FCS/Trailer: error detection bits added

Encapsulation flow

Key takeaway: IP addresses are "end-to-end" — they identify the original source and final destination. MAC addresses are "hop-to-hop" — they change at every router.
Presentation script (2 min)
🎤 What to say — Phase 1: Source Packaging
[Point to PC-Accounting on the diagram]

"I'm responsible for Phase 1 — Source Packaging. This is where the data begins its journey, starting at the PC-Accounting host.

The user wants to access the web server, so a HTTP request is generated at the Application layer. As that data moves down the OSI stack, each layer wraps it with its own header — this process is called encapsulation.

[Trace down with your finger: App → Transport → Network → Data Link → Physical]

At Layer 4, the Transport layer adds a header containing port numbers, turning the data into a segment. At Layer 3, the Network layer adds an IPv4 header — this is where the source IP 192.168.10.10 and destination IP 172.16.1.99 are stamped. These IP addresses will remain unchanged for the entire journey.

At Layer 2, the Data Link layer wraps the packet into an Ethernet frame — adding a header with source MAC AA-AA and destination MAC BB-BB, which is R1's interface, not the web server. We address it to the router because the destination is on a different network. A FCS trailer is also added for error detection.

Finally, Layer 1 converts the entire frame into bits — electrical signals — and transmits them onto the wire toward the switch and then R1."
Phase 2

Local Discovery — Is it local or remote? ARP for the gateway.

2 min

Step 1 — Determine local vs remote

PC IP: 192.168.10.10 /24 → Network: 192.168.10.0
Destination: 172.16.1.99 → Network: 172.16.1.0
Different network prefix → PC cannot reach destination directly
→ PC sends to Default Gateway: 192.168.10.1

Step 2 — Check ARP table for gateway's MAC

  • PC looks up 192.168.10.1 in its ARP cache
  • Hit → use the cached MAC address → proceed to build frame
  • Miss → must send an ARP Request first

ARP Request (broadcast)

Dst MAC: FF-FF-FF-FF-FF-FF (broadcast — all devices on the LAN receive this)
Src MAC: AA-AA
Payload: "Who has 192.168.10.1? Tell 192.168.10.10"

ARP Reply (unicast — from R1 back to PC)

Dst MAC: AA-AA Src MAC: BB-BB
Payload: "192.168.10.1 is at BB-BB"
PC stores mapping in ARP table → now builds the frame

ARP table rules

  • Maps IP address ↔ MAC address
  • Destination on same subnet: ARP for the destination's IP
  • Destination on remote network: ARP for the default gateway's IP
  • ARP broadcasts are NOT forwarded by routers — they stay on the local subnet

Resulting frame (leaving the PC)

Src MAC: AA-AA | Dst MAC: BB-BB (router's MAC)
Src IP: 192.168.10.10 | Dst IP: 172.16.1.99
Key point: The PC uses the router's MAC as the destination MAC — not the web server's MAC. The packet is handed off to the router to continue the journey.
Presentation script (2 min)
🎤 What to say — Phase 2: Local Discovery
[Point to PC-Accounting on the diagram]

"I'm covering Phase 2 — Local Discovery. Before the PC can send anything, it needs to figure out where to send it and how to address the frame.

The PC compares its own IP address — 192.168.10.10 with subnet mask /24 — against the destination IP 172.16.1.99. The network prefixes don't match, so the PC knows the destination is on a remote network. It cannot reach it directly — it must go through its default gateway, which is R1 at 192.168.10.1.

[Point to R1 on the diagram]

Now the PC needs R1's MAC address to build the Ethernet frame. It checks its ARP table. If there's no entry for 192.168.10.1, the PC sends an ARP Request — a broadcast with destination MAC FF-FF-FF-FF-FF-FF. Every device on the LAN receives this, but only R1 — the owner of 192.168.10.1 — replies.

R1 sends back a unicast ARP Reply with its MAC address BB-BB. The PC stores this in its ARP table and can now build the frame.

The resulting frame leaves the PC addressed like this: source MAC AA-AA, destination MAC BB-BB — the router — and the IP packet inside still carries the original source and destination IPs unchanged. The frame is then sent onto the local network toward R1."
Phase 3

Gateway Transition — De-encap → Route Lookup → Re-encap

2 min

Step 1 — R1 receives the frame on G0/0/0

  • NIC checks Dst MAC = BB-BB ✓ matches R1's interface → accept
  • De-encapsulation: strips the Ethernet header & FCS trailer
  • Exposes the IPv4 packet — reads Dst IP: 172.16.1.99

Step 2 — Routing table lookup

Looking up: 172.16.1.99
Match: 172.16.1.0/24 → next-hop 10.1.1.2 via interface S0/1/0
TTL decremented: 128 → 127

Step 3 — Re-encapsulation for WAN link (R1 → R2)

NEW Src MAC: CC-CC (R1 S0/1/0)
NEW Dst MAC: DD-DD (R2 S0/1/0)
IP unchanged: Src 192.168.10.10 → Dst 172.16.1.99

Step 4 — R2 repeats the process

R2 strips old L2, reads Dst IP 172.16.1.99
Match: 172.16.1.0/24 directly connected on G0/0/0
R2 ARPs for 172.16.1.99 → reply: MAC 22-22
NEW Src MAC: 11-11 (R2 G0/0/0)
NEW Dst MAC: 22-22 (Web-Server NIC)

What changes vs what stays the same

L2 Src/Dst MACChanges at every router hop — local link addressing only
L3 Src/Dst IPStays the same the entire end-to-end journey
TTLDecremented by 1 at every router; at 0 → packet discarded + ICMP Time Exceeded sent
Router's 4 L2 functions at each hop: (1) Accept frame from incoming interface → (2) De-encapsulate L2 header → (3) Consult routing table + re-encapsulate with new L2 addresses → (4) Forward new frame out correct interface.
Presentation script (2 min)
🎤 What to say — Phase 3: The Gateway Transition
[Point to R1 on the diagram]

"I'm covering Phase 3 — the Gateway Transition. This is where the router takes the frame from the local LAN and forwards it toward the destination network.

The frame arrives at R1's G0/0/0 interface. R1's NIC checks the destination MAC — it's BB-BB, which matches this interface, so R1 accepts the frame. It then de-encapsulates the Ethernet header and trailer, exposing the IPv4 packet inside.

[Point to the packet's destination IP]

R1 reads the destination IP: 172.16.1.99 and looks it up in its routing table. It finds a match — the 172.16.1.0/24 network is reachable via R2 at 10.1.1.2, out of interface S0/1/0. R1 also decrements the TTL by 1.

R1 now re-encapsulates the same IP packet into a brand new Ethernet frame for the WAN link — with a new source MAC CC-CC and destination MAC DD-DD. Notice the IP addresses inside have not changed at all.

[Point to R2 on the diagram]

When the frame reaches R2, the exact same process repeats — R2 de-encapsulates, looks up 172.16.1.99, finds it directly connected on G0/0/0, ARPs for the web server's MAC 22-22, and re-encapsulates the packet one final time before forwarding it to the server."
Phase 4

Arrival & De-encapsulation — Up the Stack to the App

2 min

Step 1 — Physical Layer (Layer 1)

  • Web-server NIC receives bits from the wire/wireless medium
  • Converts signals back into the binary frame → passes up to Layer 2

Step 2 — Data Link Layer (Layer 2) — NIC check

  • NIC reads Dst MAC in the frame header = 22-22
  • Compares against its own MAC stored in RAM → Match ✓ → accept
  • If no match → frame is silently discarded
  • Checks FCS/CRC trailer for transmission errors → if corrupted, discard
  • Strips Ethernet header + trailer → passes IPv4 packet up

Step 3 — Network Layer (Layer 3)

  • Reads Dst IP = 172.16.1.99 → matches this host ✓
  • Reads Protocol field (e.g. 0x06 = TCP) → knows what's inside
  • Strips IP header → passes segment up to Transport layer

Step 4 — Transport Layer (Layer 4)

  • Reads destination port (e.g. port 80 = HTTP)
  • Strips transport header → passes application data up
  • For this assessment: no TCP/UDP mechanism details required — just know it de-encapsulates and delivers data up.

Step 5 — Application Layer (Layer 7)

  • Web server process receives the HTTP GET request
  • Processes the request, generates HTTP response
  • Response re-encapsulated and sent back down the stack toward PC

Presentation script (2 min)
🎤 What to say — Phase 4: Arrival & De-encapsulation
[Point to the Web-Server on the diagram]

"I'm covering Phase 4 — Arrival and De-encapsulation. This is the reverse of Phase 1: the frame arrives at the web server and the data is unwrapped back up the OSI stack.

The frame arrives as bits on the wire. The Physical layer converts those signals back into a binary frame and passes it up to Layer 2.

At Layer 2, the server's NIC checks the destination MAC — 22-22. It compares this against its own hardware MAC address stored in RAM. They match, so the frame is accepted. The NIC also verifies the FCS trailer — if the CRC doesn't match, the frame is discarded as corrupted. Otherwise, the Ethernet header and trailer are stripped, and the IPv4 packet is passed up.

[Trace upward on the diagram]

At Layer 3, IP checks the destination IP — 172.16.1.99 — confirms it matches this host, reads the Protocol field to identify TCP, strips the IP header, and passes the segment up to Layer 4.

Layer 4 reads the destination port — port 80 for HTTP — strips its header, and delivers the raw application data up to Layer 7.

Finally, the web server application receives the HTTP GET request, processes it, and generates an HTTP response — which then travels back down the stack and is sent all the way back to the original PC through the same routing process in reverse."
⚡ Q&A Bank — Likely Tutor Questions & Model Answers
Does the PC try to find the web server's MAC address directly?
No. The PC compares its IP and subnet mask with the destination (172.16.1.99). The network prefixes differ, so the PC recognises it as a remote host and sends the frame to its default gateway (192.168.10.1) instead.
If the PC doesn't know the router's MAC yet, how does it get it?
It broadcasts an ARP Request to FF-FF-FF-FF-FF-FF saying "Who has 192.168.10.1?". Only R1 (owning that IP) replies unicast with its MAC BB-BB. The PC stores this in its ARP table and then builds the frame.
When the frame hits R1, what does the router do with the MAC addresses?
R1 strips the old L2 header (Src: AA-AA, Dst: BB-BB). It reads the L3 destination IP, performs a routing table lookup, then creates a brand new Ethernet frame for the next link — with new source and destination MAC addresses (CC-CC and DD-DD) for that segment.
Why do MAC addresses change at every hop, but IP addresses don't?
MAC addresses are Layer 2 (local link) identifiers — they only have meaning on a single network segment. Each new link is essentially a new "envelope." IP addresses are Layer 3 end-to-end identifiers that carry the original source and final destination across the entire routed path.
What if the destination IP was changed to 192.168.10.50 instead?
The PC would recognise it as being on the same /24 subnet. It would ARP directly for 192.168.10.50's MAC and place that MAC in the Dst MAC field — no router (default gateway) would be involved in the Layer 2 forwarding.
What happens if TTL reaches 0?
The router that decrements TTL to zero discards the packet and sends an ICMP "Time Exceeded" message back to the source IP. This prevents packets from looping forever in a network.
How does the web server's NIC know the frame is for it?
The NIC compares the incoming frame's destination MAC (22-22) against its own hardware MAC address stored in RAM. A match means the frame is accepted and passed up the stack. No match means the frame is silently discarded at Layer 2.
What is the Protocol field in the IPv4 header used for?
It identifies the Layer 4 protocol carried inside the packet — for example 0x06 = TCP, 0x11 = UDP, 0x01 = ICMP. When Layer 3 de-encapsulates the packet, it reads this field to pass the segment to the correct transport-layer handler.
What is the EtherType field in the Ethernet frame?
It identifies the Layer 3 protocol in the frame's payload — 0x0800 for IPv4, 0x86DD for IPv6, 0x0806 for ARP. The receiving NIC uses this to route the payload to the correct protocol handler after stripping the frame header.
What is the FCS / CRC trailer for?
The Frame Check Sequence is computed by the sender over the frame contents and appended as a trailer. The receiver recalculates it upon arrival. If the values differ, the frame was corrupted in transit and is discarded. This is Layer 2 error detection — not correction.
What is the difference between a unicast, broadcast, and multicast MAC?
Unicast MAC is a unique address for one specific device. Broadcast (FF-FF-FF-FF-FF-FF) is received and processed by all devices on the LAN — used by ARP. Multicast (starting 01-00-5E for IPv4) is received only by devices that have joined that specific multicast group. Broadcasts and multicasts are not forwarded by routers.
